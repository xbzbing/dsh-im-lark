# ADR-0003：回答走 Markdown 卡片，按字符与字节双上限分条

- 状态：已接受
- 日期：2026-11-19

## 背景

飞书的纯文本消息不渲染 Markdown：列表、表格、代码块都会变成一堆符号。卡片 JSON 2.0
的 `markdown` 组件能渲染，但它有两条硬限制：卡片体积 ≤ 30 KB、组件数 ≤ 200；文本
消息则是 ≤ 150 KB。回答长度由模型决定，可能远超任一上限。

## 决策

- 回答统一用 `interactive` 卡片发送；错误提示、命令回执也用卡片，保持视觉一致。
- 发送前过两道闸：按 `maxText`（默认 2000 字符）切段，再按卡片序列化后的 UTF-8
  字节数（预算 28 KiB）对半切，直到单卡装得下。
- 切点优先段落（空行，且不在代码块内）→ 行 → 硬切；代码块被切开时补上围栏，
  每段单独渲染都是合法 Markdown。
- 只对第一条消息使用 `reply`，后续分条群发，避免一串重复引用。
- 卡片 `config.update_multi` 恒为 `true`：流式更新与终态改写都要 PATCH 同一张卡。

## 后果

- Markdown 能正常显示，长回答不会因为一次超限整条丢失。
- 分条会让一次回答占多条消息配额；频控按 5 QPS 的滑动窗口排队，不丢消息。
- 卡片体积预算比平台上限低 2 KiB，留给标题、按钮与未来的字段。
- 切段后引用关系只落在第一条，用户仍能顺藤摸瓜。

## 备选

- **纯文本**：不渲染 Markdown，回答的可读性明显下降。
- **只在超限时降级为文本**：两套渲染路径，行为不一致，用户会看到时而卡片时而纯文本。
