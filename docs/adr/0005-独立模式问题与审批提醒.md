# ADR-0005：独立模式接管问题与审批提醒

- 状态：已接受
- 日期：2026-11-21

## 背景

V0.1 把「问题/审批提醒」整体划给核心：独立模式不实现，只在核心模式下由核心发卡片。
实际使用里，主人不在 Web 端时，DSH 的提问会一直等到超时，工具授权会按缺省失败关闭——
飞书通道明明在线，却帮不上忙。

独立模式下没有核心，插件就是唯一能把「有东西在等主人」送到他手边的角色。难点有三：
Web 与飞书可能同时有人在等；两边都答会重复或矛盾；审批是安全边界，不能靠猜。

## 决策

- 只在**独立模式**接管：`!coreEnabled() && runtime.active && stack !== null`。条件不成立
  时原样 `next()`，行为与没装插件一致；接入核心后由核心处理，避免两处打扰。
- 监听 `user-questions/request` 与 `approval/request`，`prepend` 注册（Web 的转发监听器
  先于本插件注册，排后面永远轮不到）。
- 先 `next()` 把请求交给 Web，等 `questionDelayMinutes`（默认 5，范围 0–120）：这段时间
  在 Web 端答完，一条飞书都不发。
- 到点发提醒：**单题、有选项、非审批/计划审阅**的提问发**交互卡片**（单选成按钮、
  多选成下拉，卡片回调直接作答，作答后改终态卡）；其余一律发纯文本。两种形态都认
  文字作答：提问认选项/序号/自由输入；审批只认明确决定词
  （`批准`/`同意`/`approve`/`yes`，可带 `#N`），模糊文本不认领。
- 竞答：飞书先答就 abort 本地信号让 Web 卡片收起；Web 先答、超时、停用、切到核心时
  提醒作废，已发出的提问卡同步改成终态（「已在 Web 端作答」/「这条提醒已作废」），
  不留一张还能点的旧卡。审批超时、停用、切到核心时把请求交回 Web，绝不把「没看到」
  变成「拒绝」。
- 只提醒根会话：`agent.session.header.origin === 'subagent'` 的提问不打扰主人；审批拿不到
  来源时**拒绝接管**（失败关闭）。
- 发送目标只认主人单聊；发送限速 6 条/分钟、相邻至少 2 秒；在等上限 50 个提问 / 20 个
  审批，超出挤掉最旧的并交回 Web。
- 面板提供总开关与延迟；关掉时把在等请求交回 Web。

## 后果

- 独立模式下主人不在 Web 也能在飞书答问题、批授权；接入核心后自动停用。
- 提醒只在进程存活期间有效：重启后不补发，在等请求本身也随宿主重启消失。
- 审批的「批准」只给 `allowed-once`，不缓存、不批量；其余结局仍由宿主或 Web 收尾。
- 多题按「；」「。」或换行分段；段数对不上时整段当自由输入，多题不接受模糊作答。
- 提醒是打扰性消息，限速比平台 5 QPS 更紧；批量待授权不会一分钟内齐发。
- 卡片只是提问的**呈现**：多题、审批、自由输入与装不下的题仍退回文字；卡片发失败时
  自动退回文字，可用性不依赖卡片。

> 2026-11-22 修订：提问提醒由「一律纯文本」改为「单题有选项优先卡片」，其余不变。
> 起因是独立模式收到的问题只能打字回答，单选也要回「2」；卡片与核心模式用同一套
> 交互组件（按钮 / `multi_select_static`），回调走 `ReminderCenter.applyCardAction`，
> 与核心桥的卡片回调在入站流水线里按「提醒先认领、认不出再交给桥」分流。
>
> 同日修正：飞书的下拉多选**只能嵌在表单容器里**，必须带一个 `form_action_type: submit`
> 的按钮，选中值随回调的 `form_value` 回来（不是下拉自身的 `behaviors`）。没有提交按钮时
> 用户勾完无处可点，真机已复现；现在两种模式的提问卡都把多选包进 `form` 并读
> `form_value.answer`。参考：[表单容器](https://open.feishu.cn/document/feishu-cards/card-json-v2-components/containers/form-container)。

## 备选

- **面板轮询待答数量再发提醒**：拿不到请求对象，无法把飞书作答回传给 waterfall；且多一层
  需要和宿主内部状态对齐的轮询。
- **审批超时默认拒绝**：把「主人没看到」变成「主人拒绝」，语义错误，也会掩盖通道故障。
- **所有会话（含子代理）都提醒**：子代理的提问会淹没主人，且子代理没有可授权的工具边界。
