# 0007. 发布走 CI，预发布进 npm 频道标签

- 状态：已接受
- 日期：2026-11-22

## 背景

插件要到 npm 上，才能从「本地 `file:` 装一份注入副本」变成别人也能装的东西。参照
`dsh-git-panel` 与 `dsh-im-wechat` 的发布流水线（`.github/workflows/release.yml`），
本仓库照同一套结构：main 上的版本提交驱动、门禁与发布分成两个 job、npm 用可信发布
（OIDC）、正文入库 `docs/releases/`。

本仓库有四处不同，必须单独定：

1. **首个版本只能是占位**。npm 的可信发布要求包已经在 registry 上存在，而本包从未
   发布过；同时 README 还把核心模式的卡片实测列为待验收，首发版本也不该直接接 `latest`。
2. **需要一条可安装的预发布通道**。有了 `stage` 频道，未走到正式版的构建能给测试者
   装，又不会污染 `latest`。
3. **公开仓库的门禁必须自包含**。最初 `bridge.test.ts` 静态 import 私有核心
   `dsh-my-superagent` 的一致性套件（devDependency 指向 `file:../dsh-my-superagent`），
   干净克隆上 `npm ci` 只留一个悬空链接，测试文件直接 `ERR_MODULE_NOT_FOUND`——
   公开 CI 会红在与产品无关的地方。
4. **预发布的正文不入库**。`docs/releases/` 只留正式版：stage / rc 是过程产物，为它们
   在仓库里各留一份文档，读的人要自己判断哪份还算数；正文按版本、频道与安装命令生成
   就够了，正式的变更叙述留给第一个正式版。

## 决策

**发布只由 `.github/workflows/release.yml` 在 main 上执行；npm 走可信发布；预发布发
npm 的频道标签，`latest` 只给正式版；测试不依赖私有核心。**

1. 触发：main 上有改动到 `package.json` 的提交（即版本提交），或手动
   `workflow_dispatch`。**不手工打 tag，也不在本地 `npm publish`**（首次 bootstrap 例外，见第 5 条）。
2. 顺序：门禁（`npm ci` + `npm run check` + `npm pack` + `scripts/assert-pack.mjs`）→
   打 annotated tag `v<版本>` → `npm publish <tgz> --provenance` → 建 GitHub Release 并挂同一个 tgz。
3. **门禁 job 与发布 job 分离**：门禁要装开发依赖并执行它们的代码，所以它只读；发布
   job 不 checkout、不装依赖，只从 artifact 取 tgz，独享 `contents: write` 与
   `id-token: write`。供应链被污染的代码拿不到发布身份。
4. **预发布也发 npm，但只进频道标签**：`0.1.0-stage.1` → `stage`，`0.2.0-rc.1` → `rc`，
   频道名取版本号 `-` 之后的第一段。这是与 `dsh-git-panel` / `dsh-im-wechat`「预发布不发
   npm」的**刻意差异**：占位版必须落到 npm 上，否则名字占不住、测试者也没有安装地址。
   首个正式版才该占 `latest`；但 registry 不接受删掉 `latest`，首次发布时它会自动指向
   刚发的版本，所以首个正式版之前 `latest` 与 `stage` 指向同一个占位版，首个正式版
   发出来后覆盖它。
5. **首次发布手工 bootstrap 一次**：`npm trust` 只对已存在的包生效，所以 `0.1.0-stage.1`
   由有 2FA 的账号在本地 `npm publish --tag stage` 发出（不进 CI，也没有 provenance）。
   之后在 npmjs.com 把本仓库的 `release.yml` 配成可信发布者，后续版本全走 CI。
6. **测试自包含**：删掉 `dsh-my-superagent` 这个 devDependency，核心那套
   `runBridgeConformance` 里与本仓库相关的契约在 `test/unit/bridge.test.ts` 本地重写
   （身份与能力形状、回执、同 id 只发一次、超长正文、迟到修订）。公开 CI 与本地跑
   同一套，不再有「Runner 上跳过」的分支。
7. **正文分两种**：正式版正文入库 `docs/releases/v<版本>.md`，缺文件在 `npm publish`
   之前失败，重跑时用文件覆盖页面，不生成 `What's Changed`；预发布（stage / rc）不写
   文件，由 gate 按版本号、频道标签、安装命令和上一个正式版 tag（没有就写「首个版本」）
   生成，正文里明说「不是正式版」。
8. **固定基线**：runner 锁 `ubuntu-24.04`，node 锁 24.x（`engines` 也只支持 24+）；
   换基线是一次显式改动，不是滚标签的副作用。

## 后果

- 仓库里没有任何长期 npm 凭据；发布身份来自 workflow 的 OIDC，来源证明与仓库、workflow 文件绑定。
- `stage` / `rc` 版本在 npm 上可装（`dsh plugin --profile web add dsh-im-lark@stage`）；
  `latest` 在首个正式版之前指向占位版（无法删除），文档与 Release 正文都要写清这一点。
- 一致性契约的权威 Schema 仍在私有核心仓库；本地重写只覆盖本仓库相关的那几条，
  核心 Schema 变化由 `src/host/protocol.ts` 的边界类型先发现，而不是等 CI 去装私有包。
- 正式版的发布说明成了提交的一部分：想改 Release 正文就改文件，改网页会被下次重跑
  覆盖；预发布的正文来自 workflow，改文案要改 `release.yml`。
- 预发布也占 npm 版本号：一旦发过 `0.1.0-stage.2`，就不能再复用这个版本号。

## 备选

- **PAT / deploy key 检出私有核心再跑全量**：门禁最完整，但公开仓库要多背一个长期
  凭据，且这个凭据与发布无关，只为一套测试服务。否决。
- **保留 devDependency，缺包时动态 import 跳过**：CI 不红，但公开仓库仍挂着一个装不上的
  私有依赖，且测试结果随机器不同。否决。
- **把一致性契约 vendored 进本仓库**：CI 自包含，但等于把私有协议断言公开，而且升级
  要手工同步两份。否决。
- **预发布不发 npm**（与 `dsh-git-panel` 一致）：最省事，但首个版本没有名字可占，
  测试者也没有安装地址。否决。
- **在本地手工发每个版本**：凭据回到一个人手里，门禁与产物脱钩，不可重来。否决。
