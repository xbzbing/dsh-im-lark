# ADR-0001：长连接接收事件，运行时依赖官方 SDK

- 状态：已接受
- 日期：2026-11-19

## 背景

飞书事件订阅有两条路：Webhook（平台把事件 POST 到公网地址）与长连接（客户端主动连
平台）。我们的部署形态是本地开发机、家用 NAS 和小团队服务器，大多数没有公网入口，
也不该为收一条消息去配反向代理、TLS 证书与验签解密。

长连接只对**企业自建应用**开放，且每个应用最多 50 条连接、集群不广播（见
`docs/protocol/00-飞书开放平台事实.md` §1）。

## 决策

- 只做长连接，不做 Webhook。
- 用官方 `@larksuiteoapi/node-sdk` 承担握手、鉴权、重连与 OpenAPI 封装，版本钉死
  在 `1.76.0`，升级单独提交并跑完整门禁。
- SDK 只出现在 `src/host/lark/sdk.ts`；其余模块面向 `lark/connection.ts` 与
  `lark/api.ts` 的端口，测试注入假实现。
- 长连接只有一条：一个 profile 一个连接，不做多副本消费。

## 后果

- 装上插件、填好凭据就能收消息，不需要公网地址与证书。
- 引入了一个运行时依赖，偏离「零依赖」的偏好；换来的是不必自己实现 WS 握手、
  token 刷新与 OpenAPI 错误处理——这些自己写更容易出错，也更难跟上平台变化。
- 50 连接与「不广播」意味着不能靠多开进程水平扩展；需要横向扩展时只能改成
  Webhook + 自建分发，那是另一套架构。
- SDK 的重连不校验心跳 pong（社区反馈），所以外层加了握手超时、停滞后重建与
  状态机兜底（`connection.ts`）。

## 备选

- **Webhook**：需要公网地址与验签，家用场景不可行。
- **自写 WS 客户端**：要自己处理鉴权、心跳、重连、分片与 OpenAPI 封装，收益只是
  少一个依赖，风险与工作量都不划算。
